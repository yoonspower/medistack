# MediStack v1.0 — Potassium Salt-Form (칼륨 짝이온) name_only 정책

> 상태: **정책 문서(설계·판단만)**. 이번 작업은 **문서만** 작성하며 full index 데이터·src·validator·queue를 **변경하지 않는다.**
> 대상: full drug name index의 **name_only** 항목 중 품목명/성분명에 "칼륨"이 포함된 건.
> 선행: Phase 4 확장(`MediStack_v1.0_full_drug_index_phase4_report.md`) · 10k 계획(`MediStack_v1.0_full_drug_index_10k_plan.md`).
> 작성일: 2026-06-13 · 기준 커밋: `aef9763` (full index 5,500).

---

## 1. 배경

- MediStack에서 **칼륨은 민감 항목**이다. 표준 불변 규칙상:
  - **칼륨 제품 링크 금지** (구매/제휴/제품 링크를 칼륨에 붙이지 않는다).
  - **칼륨보존이뇨제 복합제 영구 차단** (스피로노락톤/아밀로라이드/트리암테렌/에플레레논 — HCTZ 외 복합제 basis 금지).
  - **칼륨 관련 relation은 특히 주의** (relation은 검증된 의학 판단이며 천장 = verified_reference).
- 그러나 **full drug index의 name_only 항목은 relation 정보가 아니다.** name_only는
  "검색했는데 안 나오는 약" 체감을 줄이기 위한 **품목명 확인 전용**이며, 상호작용/영양소/제품/relation을
  **표시하지 않는다.** (Phase 3 UX: name_only 카드 = "참고 정보 없음 / 품목명 확인만 가능".)
- 즉, 칼륨 민감 규칙은 **relation·제품·영양소·링크** 계층을 겨냥한 것이고, name_only의 **단순 품목명 표시**는
  그 계층에 해당하지 않는다. 본 문서는 이 경계를 명문화하고, name_only에 등장하는 칼륨 항목을
  **정책적으로 어떻게 다룰지**를 확정한다.

## 2. 발견 내용

Phase 4 확장(1,000 → 5,500) 후 full index 구성:

| 구분 | 수 |
|---|---|
| full index 총수 | **5,500** |
| relation_card (covered_by_relation=true) | 558 |
| **name_only** (covered_by_relation=false) | **4,942** |

name_only 4,942건 중 "칼륨" 포함 건은 **측정 기준에 따라 수가 다르다**:

| 측정 기준 | 칼륨 포함 건수 | 의미 |
|---|---|---|
| **item_name** (화면 표시 품목명) | **79** | 사용자가 검색 결과에서 실제로 보는 품목명에 "칼륨"이 노출되는 건 |
| **ingredient_name** (JSON 내부 성분명) | **139** | 품목의 주성분 문자열에 "칼륨"이 들어간 건 (품목명에는 안 보일 수 있음) |

### 2.1 숫자 차이(79 vs 139)의 원인

- **item_name 기준(79)**: 브랜드/품목명 자체에 "(로사르탄칼륨)", "클라불란산칼륨" 등이 노출되는 건.
- **ingredient_name 기준(139)**: 품목명에는 칼륨이 안 보이지만 주성분(`ingredient_name`) 문자열에
  칼륨염이 들어간 건까지 포함. 차이 60건은 대부분 **품목명은 브랜드명만 표기**하고 성분은 별도 필드에 둔 경우다.
  - 예) `구멘틴375밀리그램정` (품목명에 칼륨 없음) → 주성분 `아목시실린수화물/묽은클라불란산칼륨`.
  - 예) `건카브정60/5밀리그램` (품목명에 칼륨 없음) → 주성분 `피마사르탄칼륨삼수화물/에스암로디핀…`.
- **핵심**: `ingredient_name`은 **JSON 데이터에만 존재**하고 **앱 검색 인덱스에는 반입되지 않는다.**
  Phase 3 `buildNameOnlyIndex`는 `item_seq / item_name / normalized_item_name / company_name`만 복사한다.
  따라서 **사용자 UI에 실제 노출되는 칼륨 건은 79(품목명 기준)**이며, 139는 데이터 감사용 상한치다.

## 3. 분류 (전수 감사 결과)

name_only 139건(ingredient_name 기준)의 "…칼륨" 짝이온을 **정규식 전수 추출**한 결과 — 전부
**salt-form / 짝이온 / 복합제 co-ingredient**이며, **standalone 칼륨보충제는 0건**이다.

### 3.1 칼륨염 토큰 인벤토리 (ingredient_name 기준)

| 치료군 / 용도 | 칼륨염 토큰 | 토큰 출현 | 성격 |
|---|---|---|---|
| **ARB (고혈압)** | 로사르탄칼륨 | 41 | 활성성분의 염(짝이온). 칼륨은 약물 염기 |
| ARB (고혈압) | 피마사르탄칼륨(삼수화물) | 33 | 동일 |
| ARB (고혈압) | 아질사르탄메독소밀칼륨 | 9 | 동일 |
| **항생제 복합** | (묽은)클라불란산칼륨 | 32 (+오타변형 1) | 아목시실린+클라불란산 복합제의 β-락타마제 억제제 염 |
| **위장약 복합** | 비스무트시트르산염칼륨 | 7 | 라니티딘+수크랄페이트+비스무트 복합제의 짝이온 |
| **비염·감기·외용 복합** | 글리시리진산이/디칼륨 | 7 + 2 | 감초 유래 항염 성분의 칼륨염(co-ingredient) |
| **진해거담 복합** | 구아야콜설폰산칼륨 | 3 | 종합 감기·기침약의 거담 성분 염 |
| **장 정결 복합** | 황산칼륨 | 2 | 피코설페이트+황산칼륨+황산마그네슘 장정결제의 한 성분 |
| **구강용품(치약)** | 제일·제이인산칼륨 | 2 entries | 치약(외용)의 완충/연마 보조 성분 — 전신 흡수 약 아님 |
| **종합비타민·미네랄** | 요오드화칼륨 | 1 | 활성은 요오드(아이오딘); 칼륨은 짝이온 |
| **점안액 복합** | L-아스파르트산칼륨 | 1 | 8성분 복합 점안액의 미량 co-ingredient |

> 주: entry 수 = **139**, 토큰 출현 = 143. 일부 복합제(특히 치약)가 칼륨염 2종(제일인산칼륨+제이인산칼륨)을
> 동시 함유해 토큰 합이 entry 수를 약간 초과한다. 분류상 차이는 없다.

### 3.2 standalone 칼륨보충제와의 구분

본 정책에서 **차단 대상으로 보는 "standalone 칼륨보충제"**는 칼륨 자체를 보충/전해질 교정 목적으로
투여하는 단일·주성분 제제다. 전형적 형태:

- 염화칼륨(KCl) 서방정/주사
- 구연산칼륨(citrate) 단일 보충제
- 글루콘산칼륨 / 아스파르트산칼륨 **단일 전해질 보충제**
- "포타슘/칼륨/전해질 보충" 라벨 제품

**현재 full index 5,500 전수 스캔 결과 이런 standalone 칼륨보충제는 0건이다.**
- standalone 키워드 스캔의 유일한 후보(`L-아스파르트산칼륨`) 1건은 **8성분 복합 점안액**
  (`뉴브이로토이엑스점안액`)의 미량 co-ingredient로, **칼륨 보충제가 아니다.**
- 위 §3.1의 모든 건은 칼륨이 **다른 활성성분의 짝이온이거나 복합제의 부수 성분**이다.

### 3.3 칼륨보존이뇨제 누출 검사

표준 불변 규칙(칼륨보존이뇨제 복합제 영구 차단) 준수 확인:
- 스피로노락톤/아밀로라이드/트리암테렌/에플레레논 → full index 5,500 전수 스캔 **0건 누출**.
- Phase 4 수집 시 해당 성분을 `DIVERSE_INGREDIENTS`에서 의도적으로 제외했고, 결과적으로도 유입 0.

## 4. 리스크 분석

| # | 리스크 | 평가 |
|---|---|---|
| R1 | 사용자가 품목명의 "칼륨" 단어만 보고 **칼륨 보충제로 오인** | 낮음. name_only는 상호작용 카드가 아니라 "참고 정보 없음 / 품목명 확인" 만 표시. 의료적 판단·복용 지시 없음 |
| R2 | name_only에 칼륨 주의/상호작용/영양소가 **붙는 것** | **이것이 진짜 위험.** relation 없는 약에 근거 없는 칼륨 주의를 붙이면 오히려 잘못된 의학 정보가 됨 → 정책으로 **금지** |
| R3 | salt-form을 **무조건 제외**하면 검색 커버리지 손실 | 큼. 로사르탄/피마사르탄/오구멘틴류 등 **흔한 일반 처방약**이 검색에서 사라짐 → PM 목표("안 나오는 약 줄이기")에 역행 |
| R4 | 향후 10k 확장 시 **진짜 standalone 칼륨보충제 유입** | 현재 0건이나 성분 풀 확대 시 가능 → validator 보강 권장(§7) |

**결론**: 현재의 칼륨 건은 표시(R1)보다 **잘못된 의학 정보 부착(R2)**과 **과잉 제외(R3)**가 더 큰 위험이다.
name_only의 "정보 없음" 원칙을 지키는 한, salt-form 표시 자체는 안전하다.

## 5. 정책 선택지

### A. 유지 (salt-form name_only 유지)
- 칼륨 짝이온/복합제 성분 건을 name_only로 **그대로 유지**.
- relation/영양소/제품/링크/칼륨 주의 문구는 **절대 표시하지 않음**(현행 그대로).
- 장점: 검색 커버리지 보존, 데이터 무변경, UX 일관.
- 단점: 품목명에 "칼륨"이 보이는 79건은 단어만으로는 오인 여지(그러나 R1 낮음).
- **단기 추천안.**

### B. 제외 ("칼륨" 포함 name_only 전부 제외)
- item_name 또는 ingredient_name에 칼륨이 든 건을 전부 인덱스에서 제거.
- 장점: 보수적 안전.
- 단점: 검색 커버리지 손실이 큼(로사르탄/오구멘틴/ARB 복합제 등 흔한 약 누락).
  안전 이득은 명목상(name_only는 애초에 의학 정보가 없음)인데 **실손실이 큼** → 비추천.

### C. 조건부 유지 (salt-form allowlist + standalone hard block)
- salt-form/짝이온/복합제 co-ingredient는 **유지**(allowlist).
- **standalone 칼륨보충제 키워드는 hard block** (validator로 분리).
- 향후 validator에 분류 로직 추가(§7).
- 장점: 커버리지 보존 + 진짜 위험(보충제 오인) 차단의 양립.
- **장기 추천안.**

## 6. PM 추천안

| 시점 | 정책 | 근거 |
|---|---|---|
| **단기** | **A 유지** | 현재 139건 전부 salt-form이고 standalone 보충제 0건. name_only는 품목명 확인 전용·의학 정보 없음. 제외 시 실제 약 검색 커버리지 손실 |
| **중기** | **C 조건부 유지** (validator 추가) | salt-form allowlist 유지 + standalone potassium blocklist를 validator로 강제. 10k 확장에서 보충제가 유입돼도 자동 차단 |

**핵심 판단**: 현재 데이터로는 A와 C의 **실효 결과가 동일**하다(standalone 0건이므로 C의 block이 현재는 no-op).
차이는 "미래 방어"뿐이다. 따라서 **지금은 A로 유지하되, 10k 확장 전에 C의 validator를 도입**하는 단계적 접근이 옳다.

## 7. validator 제안 (✅ 구현 완료 — 2026-06-13, PM 승인)

> ✅ 본 절의 설계는 **구현·CI 배선까지 완료**되었다: `scripts/validate_potassium_name_only_policy.py`
> (+ fixture `scripts/fixtures/potassium_name_only_policy.json`, 리포트
> `docs/MediStack_v1.0_potassium_salt_form_validator_report.md`). 데이터는 **수정하지 않았다**(위반 보고만).
> 현재 데이터 PASS(8/8, blocked 0, manual-review 1) · selftest PASS(0 failures). 아래는 그 설계 명세다.

**분류 규칙**: name_only 항목의 `item_name` 또는 `ingredient_name`에 "칼륨"이 포함되면 분류한다.

**허용(allowlist) — 다른 활성성분의 짝이온 / 복합제 co-ingredient:**
- 로사르탄칼륨, 피마사르탄칼륨(삼수화물), 아질사르탄메독소밀칼륨 (ARB 염)
- (묽은)클라불란산칼륨 (아목시실린 복합 항생제)
- 글리시리진산이칼륨 / 글리시리진산디칼륨 (감초 유래 항염 co-ingredient)
- 비스무트시트르산염칼륨 (위장약 복합)
- 구아야콜설폰산칼륨 (진해거담 복합)
- 요오드화칼륨 (종합비타민 — 활성은 요오드)

**차단(blocklist) — standalone 칼륨보충제 신호:**
- 염화칼륨, 구연산칼륨(시트르산칼륨), 아스파르트산칼륨, 글루콘산칼륨, 중탄산(탄산수소)칼륨
  → **단, 단일/주성분으로 전해질·칼륨 보충 목적**일 때만 차단.
- "포타슘 보충", "칼륨 보충", "전해질 보충" 라벨 제품.

**판정 원칙 (allowlist > blocklist 충돌 해소):**
- 칼륨염이 **비-칼륨 활성성분의 염**이거나 **2성분 이상 복합제의 부수 성분**이면 → 허용.
- 칼륨염이 **유일 활성 또는 보충 목적 주성분**이면 → 차단.
- 경계 사례(예: 황산칼륨 단독 vs 장정결 복합)는 **복합제 여부**로 가른다(복합이면 허용).

**구현 시 부속물(차후):**
- validator 음성 테스트: 가짜 standalone 보충제를 주입해 차단되는지 selftest.
- 라이브 데이터 감사: 차단 후보 0건임을 리포트.
- 회귀: 허용 건(로사르탄/오구멘틴 등) name_only 유지 확인.

## 8. UX 원칙 (불변)

- name_only 카드는 **"참고 정보 없음 / 품목명 확인만 가능"** 만 표시한다.
- **칼륨 주의 문구를 name_only에 붙이지 않는다.** 칼륨 주의는 **근거 relation이 있는 경우에만**
  (relation_card 또는 HCTZ 복합제처럼 검증된 basis) 표시한다.
- name_only에 금지: `href`, 제품 링크, 구매 링크, 영양소 추천, 복용 지시, 상호작용, relation 카드.
- 이 원칙은 검증기 `FORBIDDEN_NAMEONLY_FIELDS`로 이미 강제되고 있으며, 칼륨 정책도 이를 따른다.

## 10. 결론

- 현재 칼륨 건 **139건(ingredient_name 기준) / 79건(item_name 기준)은 유지 가능**하다.
- 전부 **salt-form / 짝이온 / 복합제 co-ingredient**이며 **standalone 칼륨보충제는 0건**이다.
- 이들은 **"칼륨 제품/보충제"로 취급하지 않는다.** name_only **품목명 확인 전용**으로만 유지한다.
- relation/영양소/제품/링크/칼륨 주의 문구는 name_only에 **절대 붙이지 않는다**(기존 UX 불변).
- **10k 확장 전 validator 보강(C안)을 권장**한다: standalone potassium blocklist + salt-form allowlist를
  코드·검증기 이중 가드로 명문화하여, 성분 풀 확대 시에도 보충제 유입을 자동 차단한다.
