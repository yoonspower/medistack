# MediStack v0.3 — 로드맵 (계획서)

작성 기준일: 2026-06-07 / 단계: **계획만** (코드·데이터·DATA_URL·deploy 전부 미실행)
직전 상태: 라이브=v0.2 30건(`yoonspower.github.io/medistack`), 태그 `v0.2-beta`→`10ef892`, main 단일 브랜치, validator v0.1 12/12·v0.2 15/15.
짝 문서: `docs/MediStack_v0.2_release_notes.md`(§7 v0.3 후보), `docs/MediStack_v0.2_phase3_release_plan.md`(배포 SOP 재사용).

> 이 문서는 방향·우선순위·검증 게이트만 정의한다. 실제 데이터 편입·코드 변경·배포는 각 트랙별로 PM 판정 후 별도 실행한다.

---

## 0. 불변 원칙 (v0.3에서도 유지)
- 원문(식약처 허가사항 사용상의 주의사항)에 없으면 **노출 금지**.
- 원문보다 강한 해석(부작용 목록 → 모니터링 지시 등) **금지**.
- 복용량·제품추천 표현 **금지**. 칼륨 행 제품 링크/예시/구매 버튼 **금지**(`product_link_allowed=false`).
- clinical reviewer 확보 전 `published`/`clinical_reviewed` **봉인**(천장 = `verified_reference`).
- 모든 상세에 `disclaimers.common` fail-safe 표시.
- **validator PASS 없으면 배포 금지.** v0.1 JSON 봉인(md5 불변)·v0.2 데이터 무수정 유지.
- v0.2 데이터(30건)는 append-only 원칙. 기존 행 의미 변경은 별도 재검증 트랙으로만.

---

## 1. v0.3 목표 한 줄
사용자가 **상품명으로도 찾을 수 있고**, **검색 결과 없음이 '안전'으로 오인되지 않으며**, 검증된 관계가 **단계적으로 더 많아지는** 베타. 데이터 신뢰도 SOP는 v0.2와 동일(원문 직접 검증).

---

## 2. 트랙 분류 (UX 트랙 vs 데이터 트랙)

v0.3은 성격이 다른 두 묶음으로 나눈다. 섞으면 PR이 비대해지고 롤백 단위가 흐려진다.

| 트랙 | 항목 | 데이터 원문검증 필요 | 라이브 안전영향 | 권장 순서 |
|---|---|---|---|---|
| UX-A | 제품명 alias 검색 | 불필요(런타임 인덱스) | 낮음 | 1순위 |
| UX-B | 미등록 약 안내 UX | 불필요(문구·라우팅) | **중**(오인 방지 = 안전 직결) | 1순위(UX-A와 묶음 가능) |
| OPS-C | 사용자 검색 기반 후보 관리 | 불필요(운영 트랙) | 없음(내부) | 2순위 |
| DATA-D | 30→목표 확장 | **필수**(행별 원문 SOP) | 중(노출 콘텐츠 증가) | 상시·점진 |

원칙: **UX 트랙과 DATA 트랙은 별도 PR.** UX는 코드만, DATA는 데이터+validator만 건드리도록 분리.

## 3. 트랙별 상세

### UX-A. 제품명(브랜드/상품명) alias 검색
- **문제:** 현재 검색은 성분명·영양소명 기준. 사용자는 "타리비드"·"포사맥스"·"넥시움" 같은 상품명으로 찾는다.
- **방향:** 데이터에 이미 있는 대표품목명(예: 제일타리비드정, 포사맥스70밀리그램정)을 **런타임 alias 인덱스**로 만들어 검색 매칭에 포함. 데이터는 append-only(필요 시 행에 `product_aliases: []` 필드 추가, 기존 의미 불변).
- **안전 가드:**
  - alias는 **이미 검증된 관계 행에 연결된 품목명에 한정.** 새 약물·새 관계를 alias로 끌어들이지 않는다.
  - 상품명 매칭은 그 행의 검증된 관계로만 연결(상품명이 "안전/위험 단정"으로 읽히는 카피 금지).
  - 동일 성분 다수 제네릭을 전부 넣지 않는다. v0.2 pointer가 인용한 대표품목 + 교차확인 품목 수준만.
- **검증 게이트:** validator에 "alias는 relations 내 품목에서만 도출"(외부 약물 미유입) 체크 추가 검토. 로컬 QA: "타리비드"→오플록사신 21~23, "포사맥스"→알렌드론산 29, "넥시움"은 **15행 excluded이므로 미노출**(중요: 상품명 검색이 excluded 우회 경로가 되면 안 됨).

### UX-B. 미등록 약 안내 UX
- **문제:** 검색 결과 0건이 "이 약은 영양소와 상호작용이 없다(안전)"로 오인될 수 있다. v0.2 QA에서 이미 "무매치 ↔ empty_state 문구 분리"를 확인했지만, v0.3은 **명시적 안내 카피 + 요청 경로**로 강화.
- **방향:**
  - 검색 무매치 시: "MediStack은 일부 약-영양소 관계만 수록한 참고 베타입니다. 결과 없음이 '상호작용 없음/안전'을 뜻하지 않습니다. 복용 관련은 의사·약사와 상담하세요." 류의 명시 문구(정확 카피는 작성 시 확정).
  - (선택) 미등록 약 **요청 경로**: 외부 폼/메일 링크 등 정적 사이트로 가능한 최소 형태. 개인정보 수집 최소화.
- **안전 가드:** "안전" 단정 절대 금지. 진단·복약지시 표현 금지. 요청 경로는 데이터 수집·자동편입과 분리(편입은 항상 원문 SOP 수동 트랙).
- **검증 게이트:** 무매치 화면 스냅샷 QA. "있을 법하지만 미수록" 약물명(예: 와파린) 검색 시 안내 문구 정확 노출 + 오인 카피 부재.

### OPS-C. 사용자 검색 기반 후보 관리 (운영 트랙)
- **문제:** 어떤 약/영양소를 다음에 검증·편입할지 우선순위 근거가 없다.
- **방향:** 미등록·빈결과 검색 쿼리를 확장 후보 큐레이션에 활용. **정적 사이트 제약상 클라이언트 로깅은 개인정보·동의 이슈**가 있으므로, v0.3에서는 가벼운 형태로 한정:
  - 1안: 별도 백엔드 없이 **사용자 요청 폼 집계**(UX-B의 요청 경로)만 후보 소스로.
  - 2안(보류 후보): 익명 검색 카운트 — 동의·프라이버시 고지·저장소 필요 → 범위·법적 검토 전 보류.
- **안전 가드:** 어떤 자동 집계도 **자동 편입으로 직결되지 않음.** 후보 → 원문 검증 SOP → validator → PR의 기존 게이트를 그대로 통과해야 노출.
- **산출물:** `docs` 내 후보 큐 파일(예: `MediStack_expansion_candidates.md`) 운영. 코드 영향 없음.

### DATA-D. 관계 확장 (30 → 목표)
- **문제:** 30건은 약효군 커버리지가 좁다. release notes는 "100건 목표"를 명시.
- **방향(점진):** v0.2 SOP 그대로 — **약효군 단위 배치**로 확장. 한 배치 = 한 약효군(또는 인접군), 행별 itemSeq + 사용상의 주의사항 번호항 직접 문구 + (신규클래스·안전민감은) 2번째 품목 교차확인.
- **후보 약효군(검증 전 가설, 편입 보장 아님):**
  - 추가 플루오로퀴놀론/테트라사이클린 품목(킬레이션 패턴 확장).
  - 갑상선호르몬(레보티록신) × 칼슘/철분 — **단, 마그네슘은 v0.2에서 원문 문구 없음으로 제외했음**(레보티록신×Mg 재시도 금지, 칼슘·철분만 원문 확인 후).
  - 경구 항응고/기타군은 **원문에 영양소 흡수·결핍·모니터링 직접 문구가 있을 때만.** 식이(비타민K 등)는 "원문보다 강한 해석" 위험 높음 → 보수적.
- **안전 가드(v0.2와 동일, 반복):**
  - 이상반응 목록만으로 편입 **금지**. 주의사항 번호항 직접 문구 필수.
  - antagonism·임상판단(clinical judgment) 행 **제외**.
  - WebFetch 단독 검증 **금지**(주의사항은 JS 렌더 → gstack browse로 원문 직접 추출).
  - 원문보다 강하면 **제외**(v0.2의 목시×칼슘·레보×Mg 제외 선례 준수).
  - 칼륨 신규 행은 `potassium_safety_card=true` + `product_link_allowed=false` 강제.
- **검증 게이트:** 배치마다 v0.2 validator(15항목) 통과 + `meta.relation_count` 동기화 + 신규행 원문 quote를 `docs`에 기록(v0.2 phase2 recheck 문서 포맷 재사용).
- **배포:** v0.2 phase3 release plan의 SOP 그대로(DATA_URL은 이미 v0.2 파일을 가리키므로, **같은 파일에 append하면 DATA_URL 변경 불필요** — 단순 데이터 PR). 단, "베타 데이터 변경"이 배포되므로 라이브 QA(목록 카운트·검색·칼륨·excluded 15) 필수.

## 4. 버전 운용 결정 (PM 판정 필요)
DATA-D를 "v0.2 파일 append"로 갈지, "v0.3 신규 export 파일 + DATA_URL 전환"으로 갈지 선택지:

- **옵션 1 (append, 가벼움):** `medistack_v0.2_beta_export.json`에 행 추가, `relation_count` 증가. validator는 그대로. DATA_URL·deploy 게이트 변경 없음. 단점: "v0.2"라는 이름에 30+α가 섞임(태그/네이밍 혼동 가능).
- **옵션 2 (v0.3 신규 파일, 명확):** `medistack_v0.3_beta_export.json` 생성 + v0.3 validator + DATA_URL 전환 + deploy 게이트에 v0.3 추가(v0.1·v0.2·v0.3 다단 검증). v0.2 SOP를 한 번 더 반복. 단점: 작업량↑.
- **권장(초안):** UX-only 변경이면 옵션 무관(데이터 안 건드림). DATA 확장이 본격화되면 **옵션 2**가 봉인/롤백/네이밍이 깔끔. 소량 행 추가뿐이면 옵션 1도 허용. → **PM이 트랙 착수 시점에 결정.**

## 5. 권장 실행 순서 (게이트)
1. **(이 문서 승인)** v0.3 방향·트랙 확정.
2. **UX-A + UX-B 묶음** (코드 PR, 데이터 무변경) → 로컬 QA(alias 매칭·excluded 우회 차단·무매치 안내) → PM 판정 → 배포.
3. **OPS-C** 후보 큐 문서 운영 시작(코드 영향 없음).
4. **DATA-D 배치 1** (약효군 1개) → 원문 검증·docs 기록·validator → §4 버전옵션 결정 → PM 판정 → 배포.
5. 이후 DATA-D 배치 반복(품질 우선, 건수는 부차).
6. 일정 분량 도달 시 `v0.3-beta` 태그 + 릴리즈 노트(v0.2 포맷 재사용).

각 게이트는 직전 단계 보고·PM 승인 없이 진행 금지.

---

## 6. 비범위 (v0.3에서 안 함)
- `published`/`clinical_reviewed` 승격 — clinical reviewer 확보 별도 트랙 전까지 봉인.
- 제품 제휴·구매·가격 UI — 전면 금지 유지.
- 자동 데이터 편입(크롤러·LLM 생성행) — 항상 원문 수동 SOP만.
- v0.1 데이터 수정 — 봉인 영구.
- 익명 검색 로깅(OPS-C 2안) — 프라이버시·동의 검토 전 보류.
