## 2. 우리영양소 앱 연동 = 커머스 아님 (비-커머스 경계 계약)

본 절은 **하드 룰**이다. "우리영양소" 앱과의 연동은 **사용자가 직접 등록한 영양소 목록의 데이터 이동(import/export) 편의**까지이며, 어떤 제품 거래로도 이어지지 않는다. 이는 `..._supplement_app_separation_strategy.md` §5 경계 계약을 **연동 시나리오로 확장 적용**한 것이다.

### 2.1 연동이 무엇인가 (허용 범위 — 이게 전부다)

- ✅ **사용자가 직접 등록한 영양소 목록의 import/export.** 내가 "지금 먹는 영양소" 목록을 한쪽 앱에서 내보내(JSON) 다른 쪽 앱에서 가져와 **같이 본다** — 그 수준의 데이터 이동뿐.
- ✅ 연동의 본질 = **"내가 먹는 영양소 목록을 두 앱에서 같이 보기".** 목록은 사용자가 손수 등록한 것이며, 앱이 "이걸 등록하라"고 추천해서 생긴 것이 아니다.
- ✅ 교환 포맷 = 로컬 파일(JSON) 수준. saved_stack 의 내보내기/가져오기(`..._saved_stack_mvp_design_v1_2.md` §7.2) 정신 승계 — 서버 경유·계정 결합 없이 사용자 책임 하 이동.

### 2.2 연동이 무엇이 아닌가 (금지 — 커머스 동선 0)

- 🚫 **제품 추천 금지.** "이 영양소엔 이 제품을 사세요/드세요" 류 동선 없음.
- 🚫 **구매 버튼·구매 링크·결제 동선 금지.** 연동 화면 어디에도 상거래 입구 없음.
- 🚫 **제휴(affiliate)·추천 랭킹 금지.** "베스트 영양제"·"추천 제품"·제휴 코드·쿠폰 없음.
- 🚫 **우회 판매 퍼널 금지.** "MediStack → 우리영양소 → 구매" 같은 단계적 동선 **0.** 두 앱을 거쳐 결국 구매로 흘러드는 어떤 경로도 만들지 않는다.
- 🚫 **약-결과 입력 → 영양제 추천 결합 금지.** MediStack 의 약 검색 결과를 우리영양소 앱의 추천/비교 입력으로 흘려보내지 않는다(§5.1 데이터 경계 승계).
- 🚫 **MediStack 신뢰 차용 금지.** "MediStack 추천 영양제" / "약사 검수 영양제" 류 라벨 없음(브랜드 경계 승계).

### 2.3 금지되는 구체 형태 (이런 모양이면 전부 위반)

추상 원칙을 못 알아보고 통과시키는 일을 막기 위한 체크리스트다. 설계·기획·구현 어느 단계든 이런 모양이 보이면 즉시 차단·되돌린다.

| # | 금지되는 구체 형태 | 위반 축 | 올바른 대안 |
|---|---|---|---|
| 1 | MediStack 약 상세 하단 "이 약과 관련된 영양소를 우리영양소에서 구매 →" | 우회 판매 퍼널 §2.2 | 버튼 없음. 연동은 사용자 등록 목록 import/export 까지만 |
| 2 | 우리영양소가 MediStack 약 검색 결과를 받아 "이 약 복용 중이면 이 제품" 표시 | 약-결과 결합 §2.2 | 약 입력을 받지 않음. 사용자 등록 영양소 목록만 교환 |
| 3 | 연동된 영양소 목록 옆에 "지금 구매" / "최저가" / 제휴 링크 노출 | 구매 동선 §2.2 | 목록은 "내가 먹는 것 보기"까지. 구매 입구 0 |
| 4 | "MediStack 와 연동된 추천 영양제 랭킹" 노출 | 추천 랭킹 + 신뢰 차용 §2.2 | 랭킹·추천 자체 금지. 사용자 등록 목록만 |
| 5 | import 한 목록을 근거로 "부족 성분이니 이 제품 보충" 푸시 | 추천 + 복용 유도 §2.2 | 행동 유도 없음. 목록 표시·이동까지만 |

> 위 5가지는 "편의"·"자연스러운 동선"으로 포장돼 들어오기 쉽다. 그러나 전부 **목록 공유를 구매의 입구로 전용**한다. 어떤 명분이든 §2.2 가 우선한다.

### 2.4 자가 점검(self-test) — 연동 기능 채택 전 1문항

> **"이 연동 기능이 사용자가 직접 등록한 영양소 목록의 단순 이동(import/export)을 넘어, 제품 추천·구매·제휴·랭킹 또는 약-결과 결합으로 이어지는가?" → 예이면 채택하지 않는다.**

이 한 문항을 통과하지 못하는 모든 제안은 그 반대(명시적 금지)로 처리한다. **연동을 커머스로 만드는 방향의 "개선"은 개선이 아니다.**

## 3. saved_stack / 가족 프로필 / 그룹 초대 = 지금 구현 금지 (동결)

- 🚫 **saved_stack(내 약 목록 저장)·가족 프로필·그룹 초대는 이번 단계 구현하지 않는다.** 건강정보 수집 이슈가 있으므로 보류한다. 설계는 `..._saved_stack_mvp_design_v1_2.md` 에 동결돼 있고, 본 문서는 그 **동결 상태를 재확인**한다.
- 🚫 **그룹 초대(여러 사용자가 한 목록을 공유·초대)는 설계 범위 밖.** 다중 사용자 결합은 건강정보 결합 표면을 키우므로, saved_stack 단독이 풀리기 전까지 **언급만 금지**가 아니라 **검토 자체 보류**다.
- ✅ 해제 조건 = 본 문서 §1 의 1순위(coverage) 달성 **+** §4 프라이버시 요건 충족 **+** PM 승인. 그 전까지 saved_stack·가족 프로필·그룹 초대 어느 것도 코드/스키마/배선을 만들지 않는다.

> 동결의 의미: 설계 문서를 더 다듬는 것은 가능하나, **localStorage·서버·계정·동기화 어느 것도 구현 착수 금지.** `..._v1_2_release_readiness.md` §8(5·6번 보류)·`..._supabase_migration_strategy_v1_2.md`(커버리지 우선 게이트)와 동일 입장.

## 4. 실제 구현 시 프라이버시 요건 (지금 미리 못박는 하드 라인)

saved_stack·가족 프로필이 **언젠가 풀릴 때**, 다음 요건을 **그 시점에 처음 고민하는 것이 아니라 지금 미리 못박는다.** 이는 `..._saved_stack_mvp_design_v1_2.md` §5·§7 과 `..._supabase_migration_strategy_v1_2.md` §5 의 하드 라인을 **장기 요건으로 승계·강화**한 것이다.

| 요건 | 내용 | 정본 참조 |
|---|---|---|
| **개인정보 동의** | 어떤 개인정보·건강 관련 데이터를 다루기 전 명시 동의. 동의 없이 수집·저장 경로 0. | saved_stack §5 |
| **로컬 저장 우선(local-only 기본)** | 기본값은 기기 로컬(`local_only=true`). 서버 저장은 옵트인이며 기본이 아니다. | saved_stack §5·§4, supabase §5.3 |
| **서버 저장 시 암호화·RLS·삭제권** | 서버에 닿는 순간 — 전송/저장 암호화, 모든 user 테이블 RLS(`auth.uid()` 본인 행만), 본인 데이터 즉시·완전 삭제(account cascade) 보장. | supabase §5.1·§5.3 |
| **가족 정보 등록 시 본인 동의 안내** | 가족 프로필은 **호칭 라벨**까지이며, 타인 건강정보를 대신 저장하는 "가족 의료기록"이 아니다. 가족 정보 등록 화면에 **본인(등록 대상) 동의 안내** 명시. | saved_stack §6 |
| **복용량·진단명·질환명·증상 컬럼 미생성** | 이 필드들의 **입력 경로 자체를 만들지 않는 것이 1차 방어선.** 안내 문구는 2차 방어선. | saved_stack §5, supabase §5.2 |

> 1차 방어선 = **입력 필드를 안 만든다.** 복용량(용량/횟수/시간)·진단명·질환명·증상을 구조화 입력하는 UI 를 두지 않으면, 사용자가 민감정보를 구조적으로 쌓을 경로가 없다. 자유 텍스트 메모(있다면)에는 민감정보 입력 금지 안내가 붙고 플레이스홀더가 복용량/진단을 유도하지 않는다(중립 문구).

> `local_only` true→false(서버 업로드) 전환은 위 요건 전체를 **다시 통과**해야 하는 변경이다(saved_stack §5 가드 재통과). 개인정보 처리방침·동의·보안이 선행되지 않은 서버 저장은 NO-GO.

## 5. 약사 참여 = 추천 권한 확보 아님 (역할 한정)

약사 참여는 **참고정보의 신뢰·품질을 높이는 검수/자문 역할**에 한정한다. 제품을 추천·판매하거나 영양제 랭킹을 만드는 권한이 **아니다.** clinical/품질 검수 트랙(`..._v1.0_clinical_reviewer_checklist.md`)과 연계되며, published/clinical_reviewed=false 봉인 해제는 **reviewer 확보 후 별도 버전**에서만 다룬다(`CLAUDE.md` §1·§6).

### 5.1 약사가 하는 일 (허용 — 이게 전부다)

- ✅ **relation 문구 검수.** 참고정보 카드의 표현이 허가사항 원문을 넘지 않는지, 단정·과장이 없는지 검토.
- ✅ **품질 자문.** 데이터 정확성·면책 톤·출처 표기에 대한 자문.
- ✅ **상담 연결 신뢰 확보.** "전문가에게 물어보라"는 톤의 신뢰를 뒷받침(상담 준비 가치, `..._free_plus_plan_v1_2.md` §5 와 정합).

### 5.2 약사가 하지 않는 일 (금지 — 추천 동선 0)

- 🚫 **제품 추천·판매 금지.** 약사 이름으로 특정 영양제를 추천·판매하는 동선 0.
- 🚫 **영양제 랭킹 생성 금지.** "약사가 고른 영양제"·"약사 추천 랭킹" 류 0.
