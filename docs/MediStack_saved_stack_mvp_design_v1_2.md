## 0. 한 줄 정의

**Saved Stack = "내가 복용·관심 있는 약을 검색해서 내 목록에 담아 두고, 그 약들에 연결된 참고정보를 모아 보고, 약사·의사에게 물어볼 질문을 준비"하는 개인 정리 도구.** 저장은 **기기 로컬(localStorage)** 한정이며, 서버·계정·백엔드가 없다. 복용 지시·해석·의학 판단은 일절 생성하지 않는다.

> 한 줄 테스트(전략 §6 승계): "이 기능이 사용자 대신 의학적 결정을 내리거나 그렇게 보이게 하는가?" → 예이면 채택하지 않는다. Saved Stack 은 **정리·보관·상담 준비**까지만이다.

## 1. 왜 사용자가 약을 저장하는가 (동기 / 가치)

저장의 가치 축은 전략 문서의 **"개인화 + 정리/보관 + 상담 준비"** 와 동일하다. 의학 판단 대행이 아니다.

| 동기 | 사용자 시나리오 | 앱이 제공하는 것 | 앱이 제공하지 **않는** 것 |
|---|---|---|---|
| **내가 뭘 먹는지 추적** | "지금 복용 중인 약 3개를 매번 다시 검색하기 번거롭다" | 검색 → 목록 저장 → 재방문 시 바로 확인 | 복용 일정·알림·복용 여부 체크(리마인더 아님) |
| **변경 확인(업데이트)** | "내 약에 연결된 참고정보 카드가 갱신됐는지 확인하고 싶다" | 저장 목록 기준 참고정보 모아보기 / (Plus 후보) 갱신 사실 고지 | "○○를 보충/중단하세요" 류 행동 유도 푸시 |
| **상담 준비** | "약사·의사에게 뭘 물어봐야 할지 정리해 가고 싶다" | 저장 목록 → 전문가에게 **물어볼 질문** 체크리스트 생성(§9) | 그 질문의 **답**·해석·결론 |

> 핵심: 저장의 본질은 "내 약 목록 메모"다. 의료기록 저장이 아니다(§7). 세 동기 모두 "정보를 더 잘 정리해 전문가 상담을 준비"하는 데 수렴한다.

> **Free 핵심 약속 불변(전략 §3):** 약 검색 · name_only 품목명 확인 · 기본 relation_card 보기 · 면책/출처/복합제 배너는 **항상 무료**다. Saved Stack 은 그 위에 얹는 정리·보관 레이어이며, **정보 접근 자체를 페이월 뒤에 가두지 않는다.**

## 3. 데이터 모델 초안 (저장 항목 스키마)

저장 단위 = **저장 항목(saved item)** 한 건. 필드는 아래 **정확히 이 목록만** 둔다(개인정보/건강정보 필드 신설 금지, §5).

| 필드 | 타입 | 의미 | 제약 / 비고 |
|---|---|---|---|
| `profile_id` | string | 프로필 식별자(가족 프로필 확장의 키, §6) | 로컬 생성 ID. 단일 프로필 MVP 에선 기본값 1개(예: `"default"`) |
| `profile_label` | string | 프로필 표시 이름(예: "나", "어머니") | **자유 입력이되 의료정보 입력 금지 안내 동반**. 증상·질환명 입력 경로 아님 |
| `saved_item_seq` | string | 저장된 약의 품목 식별자(데이터의 item_seq 계열) | MediStack 검색 결과에서만 채워짐(임의 입력 아님). 식별·매칭 키 |
| `saved_item_name` | string | 저장된 약의 품목명(표시용) | 검색 결과에서 복사. 사용자가 약명을 손으로 적는 경로 아님 |
| `ingredient_name` | string | 해당 약의 (대표) 성분명 — 참고정보 연결 보조 | 데이터에서 유래. 없으면 빈 값 가능 |
| `display_mode` | enum | 이 항목이 앱에서 어떻게 표시되는지: `relation_card` \| `name_only` | 저장 시점 데이터 기준. **name_only 항목엔 의학정보 미부착(CLAUDE.md 규칙 승계)** |
| `relation_summary_available` | boolean | 이 약에 연결된 참고정보(relation)가 있는지 | `display_mode==='relation_card'` 면 true. 모아보기·질문 생성의 입력 신호 |
| `user_note` | string | 사용자 자유 메모(예: "아침 식후 복용 중") | **선택 입력**. 자가 기록 보관일 뿐 앱이 해석·지시 X. **복용량/진단명/질환명 입력 유도 금지(§5)** |
| `created_at` | string(ISO8601) | 저장 생성 시각 | 로컬 시각 |
| `updated_at` | string(ISO8601) | 마지막 수정 시각 | 메모/표시 변경 시 갱신 |
| `local_only` | boolean(고정 `true`) | 이 데이터가 **기기 로컬에만** 존재함을 표시 | **항상 `true`.** 서버 전송 경로가 없음을 코드·문구·스키마 3중으로 못박는 가드(§5) |

### 3.1 저장 컬렉션(전체) 형태 (개념)

```jsonc
// localStorage key 예: "medistack.saved_stack.v1"  (버전 접미사로 마이그레이션 대비)
{
  "schema_version": 1,
  "local_only": true,
  "profiles": [
    { "profile_id": "default", "profile_label": "나" }
    // 가족 프로필 확장 시 항목 추가(§6)
  ],
  "items": [
    {
      "profile_id": "default",
      "profile_label": "나",
      "saved_item_seq": "200xxxxxx",
      "saved_item_name": "○○정",
      "ingredient_name": "○○",
      "display_mode": "relation_card",
      "relation_summary_available": true,
      "user_note": "",
      "created_at": "2026-06-14T09:00:00+09:00",
      "updated_at": "2026-06-14T09:00:00+09:00",
      "local_only": true
    }
  ]
}
```

> 설계 규칙: (a) `saved_item_seq` / `saved_item_name` / `ingredient_name` / `display_mode` / `relation_summary_available` 는 **검색 결과에서 채워지는 파생값**이지 사용자 자유 입력이 아니다(약명을 손으로 적게 하지 않음). (b) 사용자 자유 입력은 `profile_label` 과 `user_note` **둘뿐**이고, 둘 다 §5 의 민감정보 입력 금지 안내가 붙는다. (c) `display_mode==='name_only'` 항목은 저장돼도 **의학정보를 부착하지 않는다**(name_only 불변 규칙).

## 4. localStorage 기반 MVP (1차 설계)

### 4.1 왜 localStorage 가 1차 선택인가 (타당성)

- **현재 구조와 정합.** MediStack 은 정적 HTML/CSS/JS(ES module) + GitHub Pages, **백엔드·계정 없음**(개인정보 정책 §1). localStorage 는 서버·로그인 없이 클라이언트에서 완결되므로 이 구조를 깨지 않는다.
- **개인정보 리스크 최소화.** 저장 데이터가 **기기를 떠나지 않는다**(`local_only=true`). 서버 보관이 없으니 "건강정보 수집·국외 이전·유출" 표면이 원천적으로 작다(§5·§7). 전략 §5 "사용자 건강정보 판매·공유 없음"과 정합.
- **운영 부담 0.** 개인 개발자 1인 운영 전제(전략 §3.1)와 맞다 — 동기화 서버·DB·인증 유지보수가 없다.

### 4.2 한계 (MVP 범위로 수용)

- **기기/브라우저 종속.** 저장은 그 기기·그 브라우저·그 출처(origin)에서만 보인다. 다른 기기·시크릿 모드·다른 브라우저에서는 보이지 않는다.
- **동기화 없음.** 여러 기기 간 자동 동기화가 없다(서버가 없으므로). 기기 간 이동은 **수동 내보내기/가져오기**(§8)로만.
- **소실 가능성.** 브라우저 데이터 삭제·사이트 데이터 정리·기기 초기화 시 사라질 수 있다. → **사용자 고지 필수**("이 목록은 이 기기에만 저장됩니다. 브라우저 데이터를 지우면 사라질 수 있습니다. 백업하려면 내보내기를 사용하세요").
- **용량.** localStorage 는 출처당 수 MB 수준. 약 목록·짧은 메모 규모에선 충분(이미지·첨부 저장 안 함).

### 4.3 마이그레이션 경로 (서버/계정 도입 시)

- localStorage key 에 **스키마 버전 접미사**(`...v1`)와 페이로드 내 `schema_version` 을 둬, 후속 스키마 변경 시 **읽기-변환-쓰기 마이그레이션**이 가능하도록 한다(append-only 정신 승계: 기존 필드 의미 불변).
- 향후 계정/동기화를 도입한다면(별도 승인·정책 갱신 전제), 본 스키마를 **그대로 직렬화해 업로드**할 수 있게 설계한다. 단 **그 시점에는 개인정보 처리방침·동의·서버 보안이 선행**되어야 하며(`local_only` 가 `false` 로 바뀌는 변경은 §5 가드를 다시 통과해야 함), **본 MVP 범위 밖**이다.
- 내보내기 파일(§8) 포맷을 마이그레이션의 사실상 표준 교환 포맷으로 둔다(로컬 → 로컬 이동, 후일 로컬 → 서버 이행의 입력).

## 5. 개인정보 / 건강정보 안전 설계 (하드 라인)

본 절은 **불변 가드**다. 구현 시 코드·문구·스키마가 모두 이를 강제해야 한다.

- **서버 저장 없음(`local_only=true`).** 저장·메모·프로필 데이터는 **서버로 전송·보관하지 않는다.** 백엔드·계정·분석 전송 경로 0(개인정보 정책 §1, 전략 §5 정합).
- **민감정보 수집 금지 — 입력 경로 자체를 만들지 않는다.**
  - **복용량(용량/횟수/시간 간격) 입력 필드 만들지 않음.** "아침 1정" 같은 구조화 복용 스케줄 입력 UI 금지(리마인더 시스템 아님, §10).
  - **진단명·질환명·증상 입력 필드 만들지 않음.** 약을 질환에 연결하는 입력 경로 0.
  - **연락처·주민등록번호·처방전/약 사진** 등 식별·건강정보 입력 경로 0(약관 §6 / 개인정보 정책 §2 승계).
- **자유 입력은 `profile_label` 과 `user_note` 뿐**이고, 둘 다 **입력 화면에 민감정보 입력 금지 안내**를 명시한다(예: "메모에 증상·질환명·복용량 등 건강정보를 적지 마세요. 이 목록은 약 이름을 정리해 두는 메모입니다"). 플레이스홀더·도움말은 **복용량/진단명을 적도록 유도하지 않는다**(예시 플레이스홀더에 "아침 식후 복용 중"처럼 **스케줄·진단을 암시하는 문구를 기본 노출하지 않음** — 중립 문구 권장).
- **프레이밍 = "약 목록 관리 메모" 수준.** UI 카피·온보딩·약관에서 본 기능을 **"의료기록 저장 서비스"로 묘사하지 않는다**(§7). "내 약 메모", "내가 찾아본 약 정리"가 톤이다.
- **면책/출처 톤 불변.** 저장 화면·모아보기·질문 생성 화면에도 공통 면책(`disclaimers.common`)과 출처 톤을 유지한다(유료라고 약화 금지, 전략 §6).
- **published/clinical_reviewed false 봉인 / "식약처 승인·법적 문제없음·약사 검수 완료" 표현 금지** — Saved Stack 화면에서도 동일.

> 정합성: 본 절은 개인정보 정책 §2(개인정보·건강정보 입력 금지)·약관 §6(건강정보 입력 금지)·전략 §5(건강정보 판매·공유 없음)와 충돌 없이 정렬된다. **입력 필드를 안 만드는 것이 1차 방어선**이고, 안내 문구가 2차 방어선이다.

## 6. 가족 프로필 확장 (multi-profile)

- 데이터 모델이 이미 `profile_id` / `profile_label` 을 항목 단위로 갖고 있어, **다중 프로필은 컬렉션 수준 확장**으로 자연스럽게 가능하다(전략 §2 "가족 프로필" 후보).
- MVP 기본은 **단일 프로필**(`profile_id="default"`, `profile_label="나"`). Plus 후보 기능으로 **프로필 추가**(예: "나", "어머니", "아이")를 열고, 각 저장 항목을 한 프로필에 귀속한다. 화면은 프로필 전환 탭/드롭다운으로 목록을 필터한다.
- **가족 프로필도 §5 가드 전부 적용** — `profile_label` 은 사람을 식별하는 실명·주민번호·연락처가 아니라 **호칭 라벨**이며, 프로필에 **질환·복용량 같은 건강정보 필드를 붙이지 않는다**(여전히 "약 목록 메모" 수준). 가족 구성원의 건강정보를 대신 저장하는 "가족 의료기록"이 아니다(§7).
- Free/Plus 경계: 가족 프로필은 **Plus 후보**(§2). Free 는 단일 프로필 + 저장 한도(후보 3개).

## 7. 삭제 / 초기화 / 내보내기·가져오기

### 7.1 삭제 / 초기화 (필수)

- **항목 단위 삭제**: 저장 목록에서 개별 약 제거(즉시 localStorage 반영, 확인 문구 1회).
- **프로필 단위 삭제**: 한 프로필과 그 항목 일괄 제거(가족 프로필 사용 시).
- **전체 초기화(리셋)**: 모든 저장 데이터(프로필·항목·메모) 일괄 삭제 → localStorage key 제거. **되돌릴 수 없음**을 명시(확인 모달). "내 약 목록 메모를 모두 지웁니다" 톤.
- 삭제는 **로컬에서 즉시 완결**(서버 호출 없음 — 삭제할 서버 데이터 자체가 없음). 사용자가 자기 데이터를 **언제든 완전히 지울 수 있다**는 점은 개인정보 관점의 강점이므로 카피로 명시.

### 7.2 내보내기 / 가져오기 (로컬 파일)

- **내보내기**: 현재 저장 컬렉션(§3.1 형태)을 **로컬 파일**(JSON)로 다운로드. 서버 업로드 없음. 백업·기기 이동·소실 대비용.
- **가져오기**: 사용자가 고른 로컬 파일을 읽어 저장 컬렉션을 **복원/병합**. 스키마 검증(필드·`schema_version`) 후 적용, 실패 시 안전하게 거부(부분 손상 데이터로 덮어쓰지 않음).
- 내보내기 파일에도 **`local_only=true`** 와 면책/주의 문구를 포함(파일을 받은 쪽도 "이건 약 목록 메모이지 의료기록이 아니다"를 인지). 내보내기 파일은 사용자 책임 하 보관(공유 시 본인 판단).
- Free/Plus: 내보내기/가져오기는 §2 의 후보 경계를 따른다(전체 백업 정도는 Free 후보, 선택적 병합 등 고급은 Plus 후보 — 목표4에서 확정).

## 8. "약사에게 물어볼 질문 생성"과의 연결

- 저장 목록(또는 한 프로필)을 입력으로, **약사·의사에게 물어볼 질문 체크리스트**를 구성한다(전략 §2·§6, Plus 후보). 입력 신호 = 저장 항목의 `relation_summary_available` / `ingredient_name` / `display_mode`.
- **생성하는 것 = 질문(문의 항목)뿐.** 예: "이 약을 장기 복용 중인데, ○○ 영양소 상태를 확인할 필요가 있는지 약사에게 문의" — **결론·답·복용지시가 아니라 물어볼 항목**이다(전략 §6 정합).
- **절대 하지 않는 것:** 질문의 **답·해석·점수·위험 등급·"보충/중단하세요"** 류 생성. 저장 목록을 근거로 새 의학 판단을 만들지 않는다(기존 relation_card 재집계·재배치까지만).
- name_only 저장 항목은 약학정보가 없으므로(불변 규칙), 그 항목 기반 질문은 **"이 약에 대한 참고정보를 약사에게 직접 문의"** 수준의 중립 항목으로만 구성(없는 의학정보를 만들어 내지 않음).
- 출력물(질문 리스트)은 화면 표시·복사 정도이며, 보관 시 동일하게 **로컬 한정**(서버 전송 없음).

> 한 줄 경계: 이 기능은 **"전문가에게 무엇을 물을지"를 정리**한다. **"전문가가 무엇을 답할지"는 절대 만들지 않는다.**

## 9. 이 기능이 **아닌 것** (What this is NOT)

- ❌ **의료기록 저장 서비스가 아니다.** "약 목록 관리 메모" 수준이다. 진단명·증상·복용량·검사수치 등 **의료기록을 보관하지 않으며 입력 경로도 만들지 않는다**(§5·§7).
- ❌ **복약 알림/리마인더 시스템이 아니다.** 복용 일정·시간 알림·복용 여부 체크·순응도 추적을 하지 않는다(복용량/스케줄 입력 필드 자체를 두지 않음, §5).
- ❌ **의학적 조언·판단·해석 도구가 아니다.** "이 약엔 ○○를 보충/중단" 같은 답·권고·위험 등급을 생성하지 않는다(전략 §6, §8 정합).
- ❌ **영양제 추천·구매·제휴 동선이 아니다.** 저장·모아보기·질문 어디에서도 제품 링크·구매 버튼·제휴 코드가 없다(CLAUDE.md 불변, 전략 §5).
- ❌ **계정/클라우드 동기화 서비스가 아니다(MVP).** 서버·로그인 없이 기기 로컬에만 저장된다(`local_only=true`). 동기화는 향후 별도 정책·승인 트랙.
- ❌ **"식약처 승인 / 법적 문제없음 / 약사 검수 완료"를 표방하지 않는다.** 베타 참고 도구이며 published/clinical_reviewed = false.

## 10. 성공 기준 (검증 가능 — v1.2 목표3 §성공기준 승계)

- (a) 저장 데이터에 **개인정보·건강정보 필드 없음** — 본 문서 §3 의 10개 필드만, 그중 자유 입력은 `profile_label`·`user_note` 뿐이며 복용량/진단명/질환명 입력 경로 0(§5).
- (b) 저장은 **클라이언트 로컬 한정**(서버 전송·계정·백엔드 0, `local_only=true`).
- (c) "내 목록"은 복용 지시·해석 없이 **사용자 자가 기록 보관**임을 화면·약관에 명시(§5·§9).
- (d) name_only 저장 항목에 **의학정보 미부착 규칙 승계**(§3 display_mode 가드).
- (e) 본 설계 문서가 **자기완결** — 다음 세션이 이 문서만으로 구현 착수 가능(데이터 모델·저장소·삭제/초기화·내보내기·질문 연결·금지선 전부 명시).
- (f) Free/Plus 수치는 **후보**로 표기, 최종은 목표4/전략 문서로 이관(§2).
