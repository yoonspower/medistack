# MediStack — name_only(품목명 확인) UX 개선 설계 (v1.2, DESIGN ONLY)

> 작성일: 2026-06-14. **설계 문서 단독 — `src/` 코드·데이터·CSS 한 줄도 변경하지 않는다.**
> 불변 하드라인: name_only 에는 **상호작용·영양소·복용지시·관리·칼륨 보충안내 등 의학정보를 일절 부착하지 않는다.** name_only 카드는 **비클릭(상세 라우팅 없음)** 이다. 문구 변경은 PM 승인 + search regression smoke 재검증 동반.
> published / clinical_reviewed = **false 유지**.

---

## 0. 한 줄 요약

검색의 ~94%(16,508 / 17,580)가 name_only(품목명 확인)로 귀결된다. 현 화면은 "참고 정보 없음" 배지 때문에 **"정보 없음 = 쓸모없음/안전함"** 으로 오해되기 쉽다. 본 설계는 의학정보를 부착하지 **않는 범위에서** ① "품목명은 확인됨"이라는 **긍정적 사실**을 앞세우고, ② "등록 정보 없음 ≠ 관계 없음"을 면책 톤으로 명료화하며, ③ 개인정보·건강정보를 **수집하지 않는** 누락 제보 동선과 ④ "약사에게 물어볼 질문"·"내 목록 저장"(Plus) 연결점을 스펙으로 정의한다.

## 1. 현재 상태 (출발점)

- 카운트: full index total **17,580** = relation_card **1,072** + name_only **16,508**.
- 렌더: `src/js/render.js` `renderNameOnlyResults(matches, notice)` —
  - 상단 고지 카드: `<div class="nameonly-notice"><span class="nobadge">참고 정보 없음</span><p>{notice}</p></div>`
  - 목록 헤더: `품목명 확인 N건`
  - 각 행(`.norow`, **비클릭**): `품목명`(noname) + `회사명`(nocompany, 있을 때)
- 기본 고지 문구(`NAME_ONLY_FALLBACK_NOTICE`, 데이터 `meta.name_only_notice` 부재 시):
  > "이 약은 MediStack의 약-영양소 참고정보 DB에 아직 등록된 항목이 없습니다. 현재는 품목명 확인만 가능합니다. 복용 판단은 약사 또는 의사와 상담하세요."
- 가드: `buildNameOnlyIndex()` 가 item_seq/item_name/normalized/company_name **만** 복사(상호작용·영양소·제품 필드는 구조적으로 미반입). `searchNameOnly()` 부분일치. relation 풀과 무관·확장 안 함.
- CSS 클래스(기존): `.nameonly-notice` / `.nobadge` / `.norow` / `.noname` / `.nocompany`.

## 2. 문제 정의 — "정보 없음" 인식 문제

1. **"참고 정보 없음" 배지의 부정 프레이밍.** 사용자는 검색에 성공(품목명 확인)했는데도 "없음"이라는 빨간 신호부터 본다 → "이 앱은 내 약을 모른다 / 쓸모없다"로 이탈.
2. **"정보 없음 = 안전"의 위험한 오해.** 등록 relation 이 없다고 해서 약-영양소 상호작용이 없는 것이 아니다(미표시 ≠ 관계 없음). 이걸 명확히 못 하면 사용자가 임의로 "괜찮구나"로 해석할 수 있다 — 면책 톤으로 차단해야 한다.
3. **다음 행동의 부재.** "없음"만 보고 끝나면 동선이 끊긴다. 의학정보를 부착하지 않으면서도 **다음 행동(약사 질문 준비 / 내 목록 저장 / 누락 제보)** 으로 연결할 수 있어야 한다.

→ 핵심: **부정("없음")이 아니라 사실("품목명은 확인됨") + 안전한 다음 행동** 으로 프레이밍 전환. 단, 의학정보는 여전히 0.

## 3. 문구 개선안 (의학정보 부착 0)

### 3.1 배지: "참고 정보 없음" → 중립 라벨
- 현 `참고 정보 없음`(nobadge) → **`품목명 확인`** 또는 **`참고정보 미등록`** 으로 변경 제안.
  - 1순위: **`품목명 확인`** — 사용자가 한 일(검색→확인)을 긍정적으로 라벨링. 목록 헤더 `품목명 확인 N건`과 일관.
  - (대안: 부정 회피가 우선이면 `참고정보 미등록` — "없음"보다 사실 중립적.)
- 배지 색/스타일은 현 중립 톤(`--ink-faint`) 유지 — 경고(빨강)·안심(초록) 어느 쪽도 아님.

### 3.2 고지 본문(notice) 개선안
현 fallback 을 아래 톤으로 교체 제안(데이터 `meta.name_only_notice` 우선 규칙은 불변 — 데이터에 값이 있으면 그것을 쓰고, fallback 만 개선):

> **"품목명은 확인되었습니다.**
> 현재 MediStack에 등록된 약-영양소 참고정보는 없습니다. 등록된 정보가 없다는 것이 **약-영양소 관계가 없다는 뜻은 아닙니다.**
> 복용 중인 영양제와의 관계는 약사 또는 의사에게 확인하세요."

권장 문구(이 문서가 제안하는 정확한 표현):
- **"품목명은 확인되었습니다."**

## 4. 다음 행동 동선 (의학정보 부착 0)

name_only 화면에서 **의학적 해석을 주지 않으면서** 사용자가 할 수 있는 안전한 다음 행동 3가지를 보조 영역(고지 카드 하단)에 둔다. 셋 다 **선택**이며 화면 위계는 고지 < 품목명 목록 < 보조 동선 순.

### 4.1 "약사에게 물어볼 질문" 연결점
- name_only 결과 하단에 **약사 상담 준비를 돕는 질문 템플릿**으로 연결(예: "이 약과 ○○(내가 먹는 영양제)을 같이 먹어도 되나요?", "복용 시간을 띄워야 하나요?").
- **이 템플릿은 답이 아니라 질문이다** — MediStack 이 관계를 판단·해석하지 않는다는 원칙을 강화한다. 질문은 약명을 placeholder 로만 끼우고 **사용자 건강정보를 입력 요구하지 않는다.**
- 의학정보 부착 아님: 화면에 표시되는 건 "물어보라"는 안내와 질문 문장 틀일 뿐, 상호작용 결론은 없다.
- 구현 시점: 질문 템플릿 자체는 정적 문구. (상세 사양은 별도 "약사 상담 준비" 설계가 다룸 — 본 문서는 연결점만 정의.)

### 4.2 "내 목록 저장"(Plus) 연결점
- 권장 문구: **"이 항목을 내 목록에 저장하고 나중에 업데이트를 확인할 수 있습니다."**
- 연결 대상: `MediStack_saved_stack_mvp_design_v1_2.md`(병행 작성 중)의 저장 기능. 그 설계의 불변 원칙 승계 —
  - 저장 데이터 = **약명/품목 식별자(item_seq, item_name)만** + 추가일/간단 메모 정도. **증상·질환·복용이력·연락처 등 개인정보·건강정보 필드 0.**
  - 저장소 = **클라이언트 로컬(localStorage)** 한정. **서버 전송·계정·백엔드 0.**
  - name_only 저장 항목에는 **의학정보 미부착 규칙 승계**(저장해도 상호작용/영양소 안 붙음).
  - "내 목록"은 복용 지시·해석이 아니라 **사용자 자가 기록 보관**임을 명시.
- name_only 와의 의미: 지금은 등록 정보가 없어도, 저장해 두면 추후 relation 이 추가될 때 사용자가 다시 찾아볼 수 있다 → "없음"을 "나중에 업데이트 확인 가능"으로 전환.
- **"업데이트 확인"은 정보 갱신 사실 고지까지만**(행동 유도 푸시·복용 알림 아님 — Free/Plus 경계 원칙과 정합).

### 4.3 "누락 제보"(약명 누락만) 동선 — 개인정보/건강정보 미수집
`MediStack_privacy_and_feedback_policy_draft.md` 의 피드백 정책을 UX 로 구체화. **건강정보 수집 0** 이 절대 조건.

- **수집 범위(허용)**: 약명 누락 제보만. 가능하면 **자유입력 없이**, 현재 검색어/선택한 품목명(item_seq·item_name)을 **사용자가 명시 동작으로** 첨부하는 형태.
- **금지 입력(수집 차단 설계)**: 증상·질환명·복용 이력·진단명·주민등록번호·연락처·이메일·처방전/약 사진 등 **개인정보·건강정보**.
- **설계 제약**:
  - 자유서술 텍스트 필드는 **두지 않거나** 최소화하고, 둘 경우 "약명만 입력. 증상·개인정보 입력 금지" 안내를 폼 안에 강제.
  - 건강정보가 수집될 가능성이 있는 형태라면 **별도 개인정보 처리방침 + 사전 동의(민감정보 처리 동의)** 가 선행되어야 하며, 그 전엔 폼 공개 금지(게이트 STOP #6).
  - 제출 채널(이메일/이슈/폼)별 데이터 보유 주체 고지(구현 단계 구체화).
- **본 단계 = 정책/UX 설계만.** 폼 구현은 본 세션 범위 밖.

## 5. 기존 렌더 구조와의 정합 (호환성 체크)

- `renderNameOnlyResults(matches, notice)` 시그니처·`.nameonly-notice`/`.norow` 구조 = **유지**. 본 설계의 변경은 (구현 시) ① 배지 텍스트(`참고 정보 없음`→`품목명 확인`), ② fallback notice 문구, ③ 고지 카드 하단 보조 동선 영역 추가 — **행(.norow) 비클릭·의학정보 0 불변.**
- `buildNameOnlyIndex()` 의 필드 화이트리스트(item_seq/item_name/normalized/company_name)·`searchNameOnly()` 부분일치 = **무변경**(의학 필드 구조적 차단 유지).
- 데이터 `meta.name_only_notice` 우선 규칙 = **유지**(fallback 만 개선; 데이터 값이 있으면 그 값 사용).
- `validate_potassium_name_only_policy`(칼륨보충제 standalone 차단) = **무영향**(name_only 에 칼륨 보충안내 부착 0 불변).
- 변경 시 **`smoke_search_regression`(A~H) name_only 케이스 갱신 스펙**: 기대 배지 텍스트·notice 문구를 새 값으로 갱신. 비클릭·카운트·필드 화이트리스트는 불변.

## 6. 이번 단계 경계 (금지 / 허용)

- ✅ 허용: 본 설계 문서 + 문구/배지 개선안 + 보조 동선(약사 질문·내 목록 저장·누락 제보) UX 스펙 + smoke 갱신 스펙.
- ❌ 금지: `render.js renderNameOnlyResults` 실변경 / `buildNameOnlyIndex` 화이트리스트 변경 / name_only 에 의학정보(상호작용·영양소·복용지시·관리·칼륨) 부착 / 행 클릭(상세 라우팅) 추가 / 데이터·DATA_URL·export 변경 / 피드백 폼 실구현 / 건강정보 수집 / published·clinical_reviewed 전환.

### 향후 별도 구현 작업 (승인 후 별개 태스크)
1. `renderNameOnlyResults` 배지 텍스트 + fallback notice 문구 교체 → `smoke_search_regression` 기대값 갱신.
2. 고지 카드 하단 보조 동선 영역 추가(약사 질문 연결 / 내 목록 저장 버튼 / 누락 제보 링크) — 의학정보 0·비클릭 행 불변.
3. 내 목록 저장 = `MediStack_saved_stack_mvp_design_v1_2.md` 구현과 연동(로컬 저장·건강정보 0).
4. 누락 제보 폼 = 개인정보/건강정보 수집 차단 설계(게이트 STOP #6) 충족 후에만 공개.

> 안전 원칙(불변): name_only 는 검색 보조이지 의학 정보가 아니다 / "정보 없음 ≠ 안전" / 등록 정보 없음 ≠ 관계 없음 / 의학정보 부착 0 / 비클릭 행 / 건강정보 미수집 / 문구 변경은 PM 승인 + smoke 재검증.
