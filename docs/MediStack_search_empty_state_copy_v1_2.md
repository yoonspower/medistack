## 0. 한 줄 요약

검색이 "정보 없음"으로 끝나도 사용자가 **실망(쓸모없음)** 하거나 **오해("없음 = 안전")** 하지 않도록, ① 부정 대신 사실로 프레이밍하고, ② "정보 없음 ≠ 안전/위험"을 면책 톤으로 명료화하며, ③ **품목명 확인(name_only)** 과 **전혀 없음(no-result)** 을 별개 empty-state로 구분해 각각의 문구를 정의한다. 핵심 면책 4문장은 **PM 지정 문구를 verbatim** 채택한다. 의학정보 부착·제품 추천·복용 지시·구매 유도 0.

## 1. 목표

relation(약-영양소 참고정보)이 없는 성분/약을 검색했을 때 발생하는 두 가지 실패 인식을 줄인다 — **구현 금지, 문서만.**

1. **실망 차단**: "없음"이라는 부정 신호가 "이 앱은 내 약을 모른다 / 쓸모없다"로 이어지는 이탈을 줄인다.
2. **오해 차단**: 등록 relation 이 없는 것이 **약-영양소 상호작용이 없다는 뜻이 아님**(미표시 ≠ 관계 없음)을 명확히 한다. 사용자가 임의로 "괜찮구나"로 해석하지 못하게 면책 톤으로 차단한다.
3. **안전한 다음 행동 연결**: "약사·의사와 상담"이라는 단 하나의 안전한 다음 행동만 안내한다(의학적 결론·제품·복용지시 0).

> 본 문서는 위 목표를 위한 **문구·화면 구분 스펙**까지만 정의한다. 렌더 변경·데이터 문구 교체·폼/버튼 구현은 본 세션 범위 밖이다.

## 2. 문구 방향 — PM 지정 안전문구 (verbatim 채택)

아래 4문장은 **PM 승인 문구를 그대로(verbatim) 사용**한다. 자유 작문·변형·강화 금지.

> 1. **"현재 준비된 약-영양소 참고정보가 없습니다."**
> 2. **"정보가 없다는 뜻이 안전하거나 위험하지 않다는 의미는 아닙니다."**
> 3. **"복용 중인 약이나 영양소가 걱정되면 약사 또는 의사와 상담하세요."**
> 4. **"MediStack은 제품 추천이나 복용 지시를 제공하지 않습니다."**

### 2.1 각 문장의 톤 역할 (왜 이 순서·이 표현인가)

| # | 문장 | 톤 역할 |
|---|---|---|
| ① | "현재 준비된 약-영양소 참고정보가 없습니다." | **사실 진술.** "준비된"으로 "DB에 아직 없을 뿐"임을 시사 — "관계가 없다"가 아님. "참고 정보 없음"의 빨간 부정 신호 대신 중립 사실로 시작. |
| ② | "정보가 없다는 뜻이 안전하거나 위험하지 않다는 의미는 아닙니다." | **오해 차단(양방향).** "안전" 단정도, "위험" 단정도 모두 부정 — §5 금지선의 핵심. "없음 = 안전"과 "없음 = 위험" 둘 다 막는다. |
| ③ | "복용 중인 약이나 영양소가 걱정되면 약사 또는 의사와 상담하세요." | **안전한 다음 행동.** 결론·지시 대신 상담 유도. 유일하게 권하는 행동이 "전문가 상담"이라 의학 판단을 MediStack 이 대신하지 않음을 강화. |
| ④ | "MediStack은 제품 추천이나 복용 지시를 제공하지 않습니다." | **기대치 관리.** 제품·추천·복용지시를 받으러 온 사용자에게 앱의 성격을 명시 → 구매/추천 오인 차단(§5). |

- 톤 프레임은 연계 문서 `relation_help_copy_v1_2` §1.1과 동일: **참고 / 상담 준비 / 판단 대신 안 함.** 사실은 중립("없습니다"), 결론은 사용자에게 주지 않음("안전합니다/위험합니다" 단정 없음).
- 위 4문장은 데이터 `disclaimers.*`(라이브 확정 문구)와 **모순되지 않는다**(진단/처방 아님 · 상담하세요 톤 일치). 단, 본 문구는 **데이터에 없는 위치(검색 empty-state)** 용 신규 안내문이며, 기존 `disclaimers.*`·`meta.name_only_notice` 문구는 **건드리지 않는 것을 기본**으로 한다.

## 3. 두 empty-state 구분 — name_only vs no-result

검색이 "정보 없음"으로 끝나는 경우는 의미가 다른 두 상태로 나뉜다. **화면도 문구도 구분**한다.

| 구분 | 내부 상태 | 사용자에게의 의미 | 검색 성공 여부 |
|---|---|---|---|
| **A. 품목명 확인** | name_only (품목명은 매칭, 등록 relation 없음) | "약 이름은 찾음. 등록된 참고정보가 아직 없음." | **부분 성공**(품목명 확인됨) |
| **B. 전혀 없음** | no-result (relation·name_only 어느 인덱스에도 매칭 0) | "검색어와 일치하는 항목 자체를 못 찾음." | 매칭 0(검색어/철자 재시도 여지) |

> 핵심: **A 는 "찾았으나 정보 미등록", B 는 "못 찾음".** A 에 B 문구("결과가 없습니다")를 쓰면 "품목명 확인"이라는 부분 성공을 지워 실망을 키운다. B 에 A 문구("품목명은 확인되었습니다")를 쓰면 거짓이 된다. 두 상태는 분리해 안내한다.

### 3.1 상태 A — 품목명 확인(name_only) 문구

> name_only 의 배지·고지 본문은 이미 `MediStack_name_only_ux_improvement_v1_2.md` §3 / `MediStack_relation_help_copy_v1_2.md` §4 에서 정의됨(배지 `품목명 확인`, "품목명은 확인되었습니다 …"). **본 문서는 그 정의를 승계**하고 변경하지 않는다. 본 empty-state 설계가 추가로 권하는 것은, name_only 고지 본문이 §2 PM 4문장과 **톤상 충돌하지 않음**을 확인하는 것뿐이다(둘 다 "등록 정보 없음 ≠ 관계 없음 / 상담하세요" 동일 프레임).

- 배지: **`품목명 확인`**(중립 라벨 — `name_only_ux_improvement` §3.1 승계).
- 고지 본문: `name_only_ux_improvement` §3.2 / `relation_help_copy` §4.2 의 권장 문구 사용(품목명은 확인됨 + 등록 정보 없음 + 관계 없다는 뜻 아님 + 상담).
- 행(`.norow`)은 **비클릭·의학정보 0** 불변.
- **본 문서는 name_only 문구를 새로 발명하지 않는다.** PM 4문장(§2)은 주로 상태 B(no-result)와 "정보 없음 일반" 면책 톤에 쓰되, name_only 와 정합되는 범위에서 보조로 재사용 가능(아래 §3.3).

### 3.2 상태 B — 전혀 없음(no-result) 문구 (PM 4문장 적용)

검색어와 일치하는 항목이 **품목명 인덱스에도 없을 때**의 empty-state. PM 지정 4문장을 이 화면의 안전 면책으로 채택한다.

- 제목/한 줄(중립, 재시도 유도 — 부정 회피):
  > **검색 결과가 없습니다.** 철자나 다른 이름(상품명·성분명)으로 다시 검색해 보세요.
  - (참고: 위 한 줄은 일반적 검색 재시도 안내. 의학적 의미 0. "안전/위험" 어휘 없음.)
- 안전 면책(PM 4문장 verbatim):
  > 현재 준비된 약-영양소 참고정보가 없습니다.
  > 정보가 없다는 뜻이 안전하거나 위험하지 않다는 의미는 아닙니다.
  > 복용 중인 약이나 영양소가 걱정되면 약사 또는 의사와 상담하세요.
  > MediStack은 제품 추천이나 복용 지시를 제공하지 않습니다.

### 3.3 두 상태 와이어(텍스트)

## 4. coverage(작업 E 5축 KPI③ search-response coverage)와의 연결

작업 E 의 5축 KPI 중 **③ search-response coverage** 는 "검색에 대해 앱이 **안전하고 의미 있는 응답**을 돌려준 비율"을 본다. 본 empty-state 설계는 **"정보 없음"을 coverage 실패가 아니라 coverage 성공으로 카운트하는 UX 논거**를 제공한다.

### 4.1 논거 — "정보 없음 = 안전응답 = coverage 성공"

- coverage 의 단위는 **"relation 을 보여줬는가"가 아니라 "안전하고 적절한 응답을 했는가"** 다. relation 풀(현재 ~1,072 relation_card / 17,580 인덱스 중 ~94% name_only)이 작은 베타 단계에서 "relation 노출"만 성공으로 보면 coverage 가 구조적으로 낮게 잡혀 무의미하다.
- 검색 결과가 **품목명 확인(A)** 이든 **전혀 없음(B)** 이든, 화면이 ① 사실을 중립적으로 알리고, ② "없음 ≠ 안전/위험"을 명시하고, ③ 상담으로 안전하게 유도하면 — 그 검색은 **사용자를 오도하지 않은 안전한 응답**이다. 이는 coverage 의 본래 목적(안전·유용)을 충족한다.
- 반대로, empty-state 가 **"안전합니다/문제없습니다"로 단정**하거나, **빈 화면·에러로 방치**하거나, **제품을 들이밀면** 그 검색은 coverage **실패**로 카운트되어야 한다(안전·유용 둘 다 깨짐).

### 4.2 coverage 카운팅 가이드 (UX 관점 — 판정은 작업 E ledger 소관)

> ⚠️ 실제 KPI 수치/게이트 판정은 작업 E 가 ground truth 다. 본 절은 **empty-state 가 어떤 조건일 때 "안전응답=성공"으로 볼 수 있는지의 UX 기준**만 제시하며, 수치를 새로 산출하거나 판정을 바꾸지 않는다.

| 응답 유형 | coverage 카운트(UX 기준) | 근거 |
|---|---|---|
| relation_card 표시 | 성공 | 등록 참고정보 정상 노출 |
| 품목명 확인(A) + 안전 고지 | **성공(안전응답)** | 품목명 확인 + "없음 ≠ 안전/위험" + 상담 유도 |
| 전혀 없음(B) + PM 4문장 | **성공(안전응답)** | 재시도 안내 + §2 면책 4문장으로 오도 0 |
| 빈 화면 / 에러 방치 | 실패 | 안전응답 아님(사용자 방치) |
| "안전합니다/문제없습니다" 단정 | 실패(위험) | 금지선 위반(§5) |
| 제품/구매/추천 노출 | 실패(정책위반) | 제품·제휴 0 원칙 위반 |

- **요지**: empty-state 를 "잘 처리하는 것" 자체가 coverage 를 끌어올리는 정공법이다. relation 을 무리하게 늘리기 전에, 정보 없는 ~94% 검색에 **안전응답을 일관되게 돌려주는 것**이 coverage·신뢰의 토대다.

## 5. 금지선 (이 문서·구현 어디에도 사용 금지)

`MediStack_relation_help_copy_v1_2.md` §1.2 금지어와 `MediStack_name_only_ux_improvement_v1_2.md` 하드라인을 그대로 승계한다.

- **안전/위험 단정 금지**: "안전합니다 / 문제없습니다 / 괜찮습니다 / 복용해도 됩니다" ❌, "위험합니다 / 먹으면 안 됩니다" ❌ (정보 없음 ≠ 안전 **그리고** ≠ 위험 — §2 ② 문장이 양방향 차단).
- **복용 지시 금지**: 드세요 / 복용하세요 / 같이 드셔도 됩니다 / 피하세요 / 끊으세요 / (지시형)띄우세요 ❌.
- **제품 추천·구매 유도 0**: 추천 영양제 / 제품 / 브랜드 / 구매 / 구입 / 할인 / 제휴 / 링크에서 사세요 ❌ (§2 ④ 문장이 명시 차단).
- **권위 단정 금지**: 검증 완료 / 의학적으로 확정 / 약사 검수 완료 / 식약처 승인 / 법적 문제 없음 / 임상적으로 입증 ❌.
- **칼륨**: empty-state 에 칼륨 보충 권유·결핍 단정 금지(칼륨 정책 무영향 — empty-state 에 의학정보·보충안내 부착 0).
- **새 단정 문구 발명 금지**: §2 PM 4문장 외에 의학적 결론을 새로 쓰지 않는다.

## 6. 기존 구조와의 정합 (호환성 체크 — 구현 시 참고)

- 상태 A(name_only) 렌더 구조(`renderNameOnlyResults`, `.nameonly-notice`/`.norow`, 비클릭·필드 화이트리스트) = **무변경**. 본 문서는 A 의 기존 정의를 승계만 한다.
- 상태 B(no-result)는 기존 안전 empty 처리(`states.js` 의 0건/에러 안전 분기)와 정합. CLAUDE.md §4 "0건 → 안전 empty, '안전합니다/복용하세요' 금지" 규칙을 위반하지 않는다.
- 데이터 `disclaimers.*`·`meta.name_only_notice` 문구 = **무변경**(empty-state 안내문은 데이터에 박지 않고 화면 안내문으로 둠 — 구현 시점 결정).
- `validate_forbidden_phrases_v1_2.py` 금지어 게이트 = 본 문서 권장 문구(§2 4문장 + §3.2 재시도 한 줄)가 게이트를 통과하는 표현임을 전제(안전/위험 단정·복용지시·구매 어휘 0). 구현 시 해당 문자열을 스캔 대상에 포함.
  - ⚠️ **단, §2 ④문장("MediStack은 제품 추천이나 복용 지시를 제공하지 않습니다.")은 "제품 추천"을 부정 형태로 포함**하므로 그대로 raw 부분문자열 게이트(`FORBIDDEN` 에 "제품 추천" 존재)에 넣으면 **false positive**가 난다. 본 라운드 전용 검증기 `validate_search_empty_state_copy_v1_2.py` 는 긍정 카피(문장1–3+재시도)만 raw 스캔하고 ④문장은 부정 고지("…제공하지 않습니다")로 별도 검사한다. 구현 시 ④문장을 중앙 스캐너에 포함하려면 **승인된 부정 고지 allowlist** 또는 negation-aware 처리가 필요하다(현재는 empty-state 전용 검증기 소관).
- 변경 시 **`smoke_search_regression` no-result/name_only 케이스 갱신 스펙**: 상태 A·B 의 기대 문구를 새 값으로 갱신, 비클릭·카운트·필드 화이트리스트·안전 empty 분기는 불변.
