# MediStack v0.3 — 운영 alias seed 파일 생성 계획서

작성 기준일: 2026-06-07 / 단계: **계획만** (운영 alias JSON 미생성, 앱 검색 미반영, DATA_URL/deploy 무변경)
상위: `alias_schema_design.md`(스키마) · `alias_seed_plan.md`(범위) · `alias_sample_validator.md`(샘플+validator 구조).

> 이 문서는 운영 alias 파일을 "무엇을·얼마나·어떤 기준으로" 채울지 계획만 정의한다. 실제 JSON 생성·validator 확장 구현·앱 반영·배포는 PM 판정 후 별도.

## 0. 전제 (못박음)
- alias = **검색 보조**. 새 의학정보 아님. **alias만으로 relation 신규생성 금지.**
- v0.3 운영 seed = **v0.2 30건에 연결된 성분/대표품목 alias만.** 전체 품목(제네릭) 대량수집은 **v0.4 이후.**
- 제품 추천·구매·제휴 UI **금지**. **15행/에스오메프라졸 제품 alias 금지** 유지.
- published/clinical 봉인 유지. v0.1 봉인·v0.2 relations 불변.

## 1. 운영 alias 파일 목적
- 샘플(7성분·25개)을 **live 14성분 전체** 커버하는 운영 인덱스로 확장.
- 같은 30건 데이터에 상품명·영문/이형 성분명·약칭 진입로를 붙여 **검색 체감 커버리지**를 올린다. 의학내용·건수 불변.

## 3. 목표 alias 개수 (정직한 상한 포함)
PM 밴드 = 100~300. live 14성분·대표품목만으로 채우는 현실 분해:

| 유형 | 성분당 | ×성분수 | 소계 |
|---|---|---|---|
| 성분명(한글 정식·염/수화물·영문 INN·영문약칭) | 2~4 | ×14 | ~40~60 |
| 대표품목 함량포함명 | 1 | ×13 | ~13 |
| 브랜드 약칭(함량/제형 제거) | 1~2 | ×13 | ~15~25 |
| v0.2 교차확인 2번째 품목(있는 성분만) | 1~2 | 일부 | ~5~15 |
| **합계(현실)** | | | **~75~115** |

- **권장 v0.3 목표 = 100~150**(품질·정규화 우선). 위 분해로 100 도달 가능, 한글/영문 이형을 표준 범위에서 더하면 ~130까지.
- **300 도달은 v0.3 범위에서 정직하지 않음**: ①제네릭 전수(=v0.4) 또는 ②용량·띄어쓰기 순열을 entry로 푸는 것(정규화로 흡수해야 할 것을 개수로 부풀림). 둘 다 v0.3 원칙 위반.
- 결론: **v0.3 = 100~150 확보, 300은 v0.4(제네릭 확장) 궤도.** (§10-PM 판정)

## 4. alias 유형별 수집 기준 (PM 5분류)
1. **성분명** — relations[].ingredient(한글 정식). 검색 기본이 이미 매칭하므로 alias는 **이형 보강용**.
2. **영문/약칭 성분명** — 영문 INN(levofloxacin…) + 표준 약칭(HCTZ). WHO INN/식약처 표기 기준. 임의 작명 금지.
   - 염/수화물 정식표기(레보플록사신수화물·목시플록사신염산염 등)도 여기 포함.
3. **대표품목명(함량포함 정식명)** — pointer가 인용한 식약처 품목명 그대로(예: 토렘정5밀리그람, 미노씬캡슐50mg, 포사맥스70밀리그램정). product alias, `item_seq` 필수.
4. **약칭/브랜드코어** — 함량·제형 접미 제거형(타리비드·토렘·미노씬·포사맥스·라식스·다이크로짇). 사용자 실검색어 근접. product alias, 같은 `item_seq`.
5. **함량/표기 변형** — 원칙 **정규화(§7) 흡수**, entry 남발 금지. 정규화로 못 잡는 핵심 변형만 명시.

수집 공통: 모든 alias는 **하나의 canonical_ingredient(라이브 성분)로만** 매핑. 영양소 매핑 금지. 다대일(한 alias→2성분) 금지.

## 5. relation_id 연결 기준
- product alias는 `source_relation_ids` = 그 성분의 **라이브 relation id 전체**(예: 오플록사신→[21,22,23]).
- `item_seq` = 그 성분 relation의 source.url itemSeq와 일치.
- 성분 alias(영문/이형)는 `source_relation_ids`/`item_seq` 없이 canonical_ingredient만으로 충분(런타임이 성분→relations 해석).
- 매칭 단일키 = canonical_ingredient. relation_id/item_seq는 추적·검증 메타.

## 6. excluded / 15행 차단 기준
- **에스오메프라졸 제품 alias 전면 금지**(15행 우회). 운영 파일에 넥시움/에소메프라정 등 미포함.
- 에스오메프라졸 **성분 alias(esomeprazole)** 편입 여부 = PM 판정(§10-1). 편입 시에도 런타임 해석은 renderable relations만 → id 16(Mg)만, **id 15(B12) 절대 미노출**.
- 모든 alias 해석은 getRenderableRelations 경유. excluded_v0_1 진입 불가.
- validator가 15·excluded 연결, 에스오메프라졸 제품 alias, excluded-only 매핑을 FAIL로 차단.

## 7. 운영 alias validator 추가 규칙 (샘플 validator 11항목 + 확장)
기존 `validate_medistack_v0_3_aliases.py` 11 checks 유지 + 운영용 확장(구현 별도):
- **(확장 A) meta.alias_count == 실제 항목 수**(relation_count 패턴, drift 방지).
- **(확장 B) lang ∈ {ko, en} enum**(현재 미강제 → 강제).
- **(확장 C) item_seq 형식**(숫자 문자열) 및 product alias는 item_seq 필수.
- **(확장 D) 정규화 충돌 가드**: 서로 다른 canonical_ingredient를 가리키는 두 alias가 동일 정규화키로 충돌하면 FAIL(현재 #3은 동일키 중복을 잡지만, "다른 성분으로 충돌"을 메시지로 명확화).
- **(확장 E, 비차단 경고) 커버리지**: live 14성분 중 alias 0개인 성분 목록을 경고 출력(FAIL 아님, 운영 완성도 점검용).
- **(확장 F) 최소 개수 게이트 여부** = PM 판정(§10-2). 도입 시 `MIN_ALIASES` 상수로.
- 회귀: v0.1/v0.2 export validator 무영향 유지.

## 8. QA 케이스 (운영 파일 + validator)
- [ ] 운영 alias validator PASS (11 + 확장). v0.1 PASS / v0.2 PASS 동반.
- [ ] live 14성분 커버리지: 제품 alias는 13성분(에스오메프라졸 제외) 전부에 ≥1.
- [ ] negative: 15연결/중복/미존재성분/에스오메프라졸제품/빈alias → 각 FAIL.
- [ ] (앱 반영 단계에서) "타리비드"→21·22·23, "포사맥스"→29, "라식스"→17·18, "HCTZ"→19·20, "levofloxacin"→1·2·3.
- [ ] (앱) "넥시움"/"에소메프라정"→**0건**→UX-B 미수록 안내. "esomeprazole"→(편입 결정 시)id16만/id15 미노출, (미편입 시)0건.
- [ ] (앱) alias 파일 제거→성분명 검색 graceful degrade. 회귀: 목록 30건/콘솔0/칼륨 3건(17·19·30)/`#/r/15` 미노출/제품·구매 UI 부재.

## 9. 앱 검색 반영 전 게이트
운영 파일 생성 ≠ 앱 반영. 단계 분리:
1. 운영 `medistack_v0.3_aliases.json` 생성 + validator(확장) PASS + v0.1/v0.2 PASS → **PM 판정**.
2. (별도 단계) 앱 검색에 alias 합류 코드 + graceful degrade + 카드 "상품명으로 검색됨" 보조표시(상세 제품UI 금지) + 로컬 QA → **PM 판정**.
3. (별도 단계) CI 게이트: validate.yml/deploy.yml 에 alias validator 추가(둘 다 PASS여야 배포) → **PM 판정**.
4. DATA_URL은 v0.2 유지(앱은 alias 파일을 별도 fetch). 배포 후 라이브 QA.
- 각 게이트 직전 단계 보고·승인 없이 진행 금지. 본 문서는 1단계 "운영 파일 생성"의 계획.

## 10. PM 판정 필요사항
1. **에스오메프라졸 성분 alias 편입 여부** — 제품 alias 금지 확정. 성분 alias(esomeprazole)는 id16만 노출/안전. 권장: **보수적 제외**(15행 기조 일관).
2. **목표 개수** — 권장 100~150(품질) vs PM 밴드 상한 300(=v0.4 제네릭 필요). v0.3 상한 확정.
3. **교차확인 2번째 품목 alias 포함 여부** — v0.2에서 교차확인한 품목명도 제품 alias로 넣을지(추적성↑/개수↑).
4. **validator 최소개수 게이트(확장 F)** 도입 여부 및 임계값.
5. **운영 파일 생성을 이번 단계에서 진행할지**, 아니면 본 계획 승인 후 별도 단계로 분리할지.
6. **정규화 강도**(용량/띄어쓰기/영문 대소문자 흡수 범위) — 과정규화 시 오매칭 위험.
